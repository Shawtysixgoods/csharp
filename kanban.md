**Техническое задание (ТЗ): Ядро Канбан-доски (аналог Trello / YouGile)**

**Контекст:**
Мы разрабатываем собственный таск-трекер. Ваша задача — спроектировать объектную модель для карточки задачи. 
Система должна уметь двигать карточки по колонкам, считать их «вес» для аналитики, а также связывать задачи с историей активности и пользователями.

Задание разделено на две части. Время на выполнение: 15–20 минут.

---

### Часть 1: Иерархия карточек 
Здесь мы описываем базовую логику задачи и то, как она меняется в зависимости от типа карточки.

#### 1. Базовый класс `KanbanTask`
Фундамент для любой задачи на доске.
* **Состояние (Свойства):**
  * `Id` (строка) — уникальный номер. Задается один раз при создании задачи.
  * `Title` (строка) — название задачи.
  * `CurrentColumn` (строка) — текущая колонка. **Важно:** статус нельзя изменить напрямую извне (`private set` или скрытое поле). При создании задача всегда попадает в колонку `"To Do"`.
* **Поведение (Методы):**
  * `virtual void MoveTo(string columnName)` — переносит задачу в новую колонку (меняет `CurrentColumn`).
  * `virtual int CalculateWeight()` — возвращает условный "вес" задачи для аналитики. По умолчанию любая задача весит `10`.

#### 2. Класс `BugTask` (Карточка бага)
Наследник базовой задачи. Баги чинить сложнее, поэтому их вес рассчитывается иначе.
* **Новое свойство:** `Severity` (int) — критичность ошибки (от 1 до 5).
* **Бизнес-правило:** Переопределите метод `CalculateWeight()`. Итоговый вес бага — это базовая оценка родительского класса (`10`), умноженная на `Severity`.

#### 3. Класс `ApprovalTask` (Задача с обязательным ревью)
Наследник базовой задачи. Такие задачи требуют согласования перед закрытием.
* **Новое свойство:** `IsApproved` (bool) — статус согласования (по умолчанию `false`).
* **Бизнес-правило:** Переопределите метод `MoveTo(...)`. Эту карточку **нельзя** переместить в колонку `"Done"`, если `IsApproved` равно `false`. В этом случае метод просто ничего не делает. Во всех остальных случаях карточка двигается как обычно.

### Часть 2: Жизненный цикл объектов (Связи)
Задаче нужны системный лог и исполнитель. Ваша цель — показать разницу в том, как эти два объекта живут в памяти и как они присоединяются к карточке `KanbanTask`. 

Создайте два дополнительных класса и свяжите их с `KanbanTask`:

#### 4. Класс `TaskAuditLog` (Системный журнал) — Строгая зависимость
Журнал хранит `CreatedAt` (DateTime) и счетчик перемещений `MoveCount` (int).
* **Бизнес-правило:** Журнал — это физическая часть самой карточки. Он не существует отдельно. 
* **Реализация:** Журнал должен создаваться (`new TaskAuditLog()`) **исключительно внутри конструктора** `KanbanTask`. Внешний код не может передать в задачу готовый журнал или заменить его. 
* **Связь с логикой:** При каждом успешном вызове метода `MoveTo` в карточке, счетчик `MoveCount` в ее внутреннем журнале должен увеличиваться на 1.

#### 5. Класс `BoardUser` (Пользователь) — Свободная зависимость
Пользователь хранит `Username` (строка) и `Email` (строка).
* **Бизнес-правило:** Пользователи — это живые люди. Они существуют в системе сами по себе и просто назначаются на задачи.
* **Реализация:** В `KanbanTask` добавьте свойство `Assignee` (исполнитель). Оно должно оставаться пустым при создании задачи, а заполняться через отдельный метод `AssignUser(BoardUser user)`, который принимает ссылку на **уже существующего** где-то в системе пользователя.
